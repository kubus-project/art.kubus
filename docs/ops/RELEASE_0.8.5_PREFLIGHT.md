## Gate order

   app SHA and prove the tested artifact is the release artifact. The current
   full-tier CI run is not itself a release artifact or a completed acceptance
   report.
2. **Backend:** resolve the exact set of backend commits and migrations needed
   by the release; review and deploy them through the backend's protected
   process before the app depends on them. Confirm schema compatibility and
   production readiness first. The existing backend master deployment is the
   baseline only.
3. **Admin:** finish exact-head browser acceptance and deploy after the backend
   contracts it uses are available. Confirm source compatibility against the
   deployed backend.

The order is a release gate sequence, not authorization to deploy. Do not
continue past a failed gate.

## Proposed protected release commands (NOT EXECUTED)

Run only after all readiness evidence and owner authorization are recorded.
Commands assume the GitHub CLI is authenticated to `kubus-project/art.kubus`.

```bash
# Refresh refs and inspect exact release ancestry.
git fetch --prune origin
git rev-parse origin/dev
git rev-parse origin/master
git rev-list --left-right --cherry-pick --count origin/master...origin/dev

# Open the release-candidate PR only after dev contains the approved candidate.
gh pr create --repo kubus-project/art.kubus --base master --head dev \
  --title "Release art.kubus 0.8.5" \
  --body-file RELEASE_0.8.5_PR_BODY.md

# After protected release PR checks and explicit merge authorization, merge
# with a merge commit using the normal protected GitHub review flow.
# Do not use gh pr merge from this preparation runbook.

# After the authorized release merge, dispatch production web only from the
# exact master head. bootstrap_web_root remains false for ordinary releases.
gh workflow run release-production.yml --repo kubus-project/art.kubus \
  --ref master -f bootstrap_web_root=false

# Mobile is independent. On the exact authorized master release SHA, dispatch
# only after the release metadata/outputs are available. The workflow resolves
# the build number from CI metadata; do not guess or copy an older build number.
gh workflow run mobile-release.yml --repo kubus-project/art.kubus \
  --ref master -f release_tag=v0.8.5 \
  -f publish_github_release=false -f prerelease=true
```

The mobile workflow verifies that its source commit is contained in `master`.
Its Android job uses protected signing, verifies APK/AAB signatures and emits
`SHA256SUMS`. iOS signing runs only when the protected environment enables it
and supplies valid signing configuration. GitHub Release publication is a
separate workflow mode; the proposed command above deliberately does not
publish. A final release owner must choose the publication mode after checking
the artifacts.

## Development reconciliation after a protected release

After the authorized `dev -> master` merge, immediately fetch both protected
heads and open a reconciliation PR from `master` back into `dev` using a
non-rewriting merge commit. The canonical check is:

```bash
git fetch --prune origin
git rev-list --left-right --cherry-pick --count origin/master...origin/dev
```

The first count must be zero before ordinary development resumes. Do not squash
the reconciliation or rewrite either protected branch.
